# MediVault – Smart & Secure Personal Health Management System

MediVault is a secure, personal health management platform designed for patients to organize, protect, and track their lifelong medical records, clinical profiles, and activity audit trails in one isolated environment.

---

## 🌟 Tech Stack

- **Frontend**: React 19 + TypeScript + Vite + Tailwind CSS v4 + Lucide Icons + React Router v7 + Axios
- **Backend**: Node.js + Express (ES Modules)
- **Database**: MongoDB + Mongoose ODM
- **Authentication**: JWT (JSON Web Tokens) + bcryptjs
- **File Management**: Multer + MongoDB GridFS (private storage, file signature validation, and size limits)

---

## 🚀 Core MVP Features (30–40% Scope)

1. **User Registration & Login**:
   - Secure sign-up with email validation and encrypted password hashing (bcrypt).
   - Every account receives a unique 19-character MediVault ID at creation; share that ID to identify an account for caregiver delegation and patient-specific clinical access. Sign-in continues to use email and password.
   - Patients can register and access their accounts immediately.
   - Insurer agents are reviewed and approved by admins of their enrolled insurer. Physicians and nurses require credential review and account approval by an administrator assigned to their selected hospital; these applications are kept out of the chief administrator's user directory. Pharmacists require credential review and pharmacy organization manager approval. Laboratory technologists require credential review and approval by their verified laboratory manager.
   - Clinical accounts have a professional type. Onboarding supports physicians, nurses, pharmacists, and laboratory technologists. Independent labs, in-house hospital labs, hospital pharmacies, independent pharmacies, and pharmacy/laboratory chain parents can apply for enrollment. Chain parents are approved by a platform administrator; after approval, chain admins create and approve their locations and manage their organization's staff.
   - Insurance agents select their company from a dropdown and receive a company-prefixed agent ID generated by MediVault.
   - Administrator accounts are provisioned by an existing system operator, never through public registration.
   - Multiple platform administrators retain global control. They create hospital entries through hospital management. Clinical staff applications, hospital laboratory applications, and hospital pharmacy applications can select only active hospitals in the MediVault directory; these entries are created by an administrator. Physician and nurse accounts are explicitly linked to the selected hospital. Hospital administrators review credentials and approve physician and nurse applications assigned to their hospitals. The chief administrator does not see these applications in the user directory. Hospital administrators are created as dedicated accounts for a selected hospital; they must change the administrator-issued temporary password at first login. Hospital administrators can view a workspace only for explicitly assigned hospitals, including linked staff, labs, and pharmacies; this administrative role does not grant patient-record access. Billing is outside this workflow.

2. **JWT Authentication & Protected Routing**:
   - Protected client-side routes via `ProtectedRoute`.
   - Express authorization middleware enforcing Bearer token verification.

3. **User Health Profile**:
   - Demographics: Full name, Date of Birth, Gender, Blood group selection (`A+`, `A-`, `B+`, `B-`, `AB+`, `AB-`, `O+`, `O-`, `Unknown`).
   - Clinical tag management: Known Allergies, Medical Conditions, Ongoing Medications.
   - Emergency contact card: Contact name, relationship, and direct phone link.
   - Every stakeholder can open **My Profile** from the navigation. Patients see their editable health profile and can save a postal address resolved from an Indian PIN code; the address is also available during account registration. Clinicians, pharmacy managers, insurance agents, and administrators see their own account details and role-specific professional or organization information. These account details are private to the signed-in user.

4. **Medical Record Upload**:
   - Supported formats: **PDF**, **PNG**, **JPG/JPEG** (up to 4 MB).
   - Metadata: Title, category, clinical notes/description, record date.
   - 6 Standard Categories:
     - *Laboratory Report*
     - *Prescription*
     - *Vaccination*
     - *Medical History*
     - *Medication*
     - *Other*

5. **Medical Records Hub**:
   - Full search across titles and clinical descriptions.
   - Category filtering pills with instant counts.
   - In-app previews for images and PDF documents, including a dedicated full-page viewer.
   - The full-page viewer rechecks authorization every 10 seconds and clears its preview if access cannot be confirmed. Copies already viewed, saved, or captured cannot be recalled.
   - Direct secure document download and safe deletion with confirmation.
   - **Patient-Controlled Laboratory Requests**: Patients can select a currently verified laboratory, share requested test names and an optional note, review request status, and cancel an open request. Physicians can order tests only for a patient with an active clinical grant lasting through the chosen access expiry. In-house lab choices are limited to verified labs linked to the selected hospital; independent labs are listed separately. Patients can revoke an open physician order early. Lab technologists can see only open orders shared with their lab until expiry/revocation and submit a PDF, PNG, or JPG result into the patient vault. This workflow does not schedule collection, process payments, or clinically validate a submitted result.
   - **Patient-Controlled Pharmacy Sharing**: Patients can share one digital prescription either with a selected currently verified hospital/independent pharmacy in the MediVault directory or with a 24-hour code. They can revoke sharing early. An approved pharmacist can see only that prescription and append per-medicine dispense statuses, quantities, and a pharmacy note. The immutable prescription is not edited; patients can review dispensing history and all access and changes are audited. Sharing is limited to direct patient accounts and digital prescriptions, not caregivers or uploaded prescription files.

6. **Personal Health Dashboard**:
   - Real-time stat cards (Total records, category counts, profile completeness score).
   - Prescription category totals include both uploaded prescription documents and digital prescriptions; ongoing profile medications are shown separately from recent prescription history. Prescription history does not confirm current medication use.
   - Emergency contact quick-dial card & blood group badge.
   - Recent records list with one-click preview.
   - Basic chronological health record timeline.
   - **Medication Reminders & Daily Adherence Tracking**: Patients and full-access proxies can configure daily reminders for current medications in India Standard Time. The dashboard includes a daily dose checklist to record whether scheduled doses were taken or skipped, displaying real-time daily adherence percentages and logging compliance events to the audit trail.

7. **Hospital Appointments**:
   - Patients and full-access proxies can select a hospital, doctor, date, and available slot from approved staff profiles.
   - The appointment directory offers a View Profile option for each listed physician and nurse, showing their approved professional type, scope/specialty, and hospital affiliation. License numbers and private contact details are not shown.
   - Medical staff configure their own working days, hours, and appointment lengths; listed free slots are confirmed immediately.
   - Booked slots are unavailable and alternative open times are offered. Requests for other times during configured working hours are sent to the doctor or their assigned staff approvers.
   - **Doctor Consultation Access Window**: Confirmed appointments automatically authorize the scheduled physician to review the patient's clinical file and records starting 30 minutes before the appointment start time until 30 minutes after the appointment ends. Physicians can directly open the patient's clinical file from the appointment calendar during this window without requiring a separate standalone access request.
   - Physicians can assign other approved physicians at their hospital to review appointment requests.
   - Patients can optionally assign an approved nurse from the same hospital while booking or for an upcoming appointment, with explicit consent to share a limited set of health-profile basics and appointment nursing notes. Assisted bookings by nurses never grant nursing access on their own; the patient must approve it afterwards through this consent flow.
   - Appointment nursing access is tied to that patient, assigned nurse, and appointment. It is available only after the appointment is confirmed, opens 30 minutes before its IST start, and expires 30 minutes after its end. The patient can revoke it at any time; cancellation or declined status also prevents access.
   - Nurses see assigned appointments in the Nursing Care workspace and can append observations and nursing notes only during the access window. Entries are linked to the appointment and audited; the assigned physician can review those entries in the patient file during the same appointment access window. This workflow does not give nurses access to prescriptions or the patient's full records.
   - **Assisted Patient Booking by Nursing Staff**: Nurses can schedule appointments on behalf of patients at their hospital's outpatient / triage desk by looking up the patient's 19-character MediVault ID (`MV-XXXX-XXXX-XXXX`), selecting a physician linked to the same hospital, choosing an available slot in IST, and recording an optional chief complaint. This flow is limited to nurses. An assisted booking does not assign the nurse or grant nursing access; the patient approves that separately. Every assisted booking is recorded under `APPOINTMENT_BOOKED_BY_STAFF` in the audit log.
   - The separate My Shifts & Team area supports weekly availability, self-reported training records, a same-hospital nurse roster with aggregate appointment counts, reusable non-patient checklists, and operational shift handovers. The team board has no patient association and rejects MediVault IDs; do not enter patient information there.
   - Before a patient's appointment access window opens, the nurse appointment list hides the patient's name and ID. The list shows appointment timing and team assignment only.

8. **Insurance Policy Marketplace**:
   - Only insurer admins can create, edit, publish, unpublish, or archive marketplace plans for their own insurance company. Agents and platform admins cannot manage plans.
   - The insurer plan assistant is available to insurer admins and uses the configured AI provider to help draft listings. Chat suggestions are not saved until an admin applies them in the plan form; the assistant does not invent plan terms or publish listings.
   - Patients can search hospitals affiliated with active, approved MediVault clinicians. These are intended MediVault cashless-network facilities; actual cashless use requires an eligible active policy and authorization. Current marketplace enrollments remain demonstrations and do not provide real coverage.
   - New plans are saved as drafts; patients see only published plans and can keep demo enrollments together in the Policies area.
   - Monthly premium dates and simulated payment history are recorded for demo enrollments. Listings and payments do not bind insurance coverage or charge money.
   - Link legacy insurance plans, enrollments, and claims that predate company references with `npm run insurance:backfill-links` from `backend`. It matches stored provider or company names to exactly one insurance company and previews by default; add `-- --apply` to write. Records that match zero or several companies are listed and left unchanged, so review them manually.
   - Remove existing enrollments for the built-in sample plans with `npm run policies:clear-legacy-demo -- --confirm` from `backend`. This only deletes enrollments whose plan IDs are `essential`, `family`, or `plus`; remote MongoDB targets additionally require `--allow-remote`.

9. **Prescription medicine search reference**:
   - Specialty-to-medicine search mappings are maintained in `frontend/data/medivault_specialty_medicine_catalog.csv` and loaded into the medical-staff prescription form.
   - Shared general entries appear alongside specialty-specific search references for the dropdown professions listed in the CSV. These are not recommendations or a claim that a medicine is suitable for every patient.
   - Active entries require prescriber validation; risk labels and clinical review flags identify additional review requirements. Clinicians may also search all active catalog entries by name or search terms, or enter a medicine manually; all results must be clinically validated.
   - AI matching uses the configured provider and returns IDs from the supplied catalog entries. Only the search phrase and catalog entries are supplied; do not enter patient details in searches. When AI is unavailable, the interface falls back to keyword matching. Search does not assess medicine suitability or generate recommendations.

10. **System & Clinical Audit Logs**:
   - Automatic background logging for:
     - `LOGIN`
     - `ACCESS_REQUESTED` / `ACCESS_REQUEST_DECIDED` / `ACCESS_REVOKED`
     - `PROFILE_UPDATE`
     - `RECORD_UPLOAD`
     - `RECORD_VIEW` / Download
     - `RECORD_DELETE`
     - `APPOINTMENT_BOOKED` / `APPOINTMENT_REVIEWED`
     - `APPOINTMENT_BOOKED_BY_STAFF`
     - `MEDICATION_REMINDER_SET` / `MEDICATION_REMINDER_REMOVED`
     - `MEDICATION_ADHERENCE_LOGGED`
     - `NURSING_ENTRY_ADDED`
     - `PRESCRIPTION_SHARED` / `PRESCRIPTION_SHARE_ACCESSED` / `PRESCRIPTION_SHARE_REVOKED`
     - `PRESCRIPTION_DISPENSE_RECORDED`
   - Complete trace with timestamps, IP addresses, and resource details.
   - Every stakeholder uses the same compact activity-list layout with a single event-type selector, India-time date range, and 20-event pagination. Events are scoped to the signed-in stakeholder; the interface shows the event, explanation, timestamp, actor, and relevant resource without a wide technical table.

10. **Strict User-Level Authorization & Security**:
   - Patients can access their own records; full-access proxies and physicians can access patient data only through authorized, patient-specific grants. Nurses use appointment-scoped access, and pharmacists can see only a prescription explicitly shared for dispensing.
   - Unauthorized attempts by other users return `403 Forbidden`.
   - Physicians request access to one identified patient, select a clinical purpose (with a required explanation for “Other”), and request an access end time. Nurses use the narrower appointment consent flow instead.
   - The patient, their authorized full-access proxy, or an administrator may approve for a chosen end time or deny the request.
   - Patients, proxies, staff, or administrators may revoke an active grant; approved access expires automatically and is enforced by the API.

11. **Future Interoperability**:
   - Future hook interfaces in `recordService.js` for:
     - Blockchain hash anchoring
     - IPFS decentralized file pinning
     - FHIR format

## ⚙️ Setup & Installation Instructions

### Prerequisites
- **Node.js** (v18 or higher)
- **MongoDB** running locally on port 27017 or a MongoDB Atlas URI

### 1. Clone & Setup Backend

```bash
cd backend

# Install backend dependencies
npm install

# Review or update environment variables (.env is preconfigured for local dev)
cp .env.example .env

# Start backend server
npm run dev
# Server will run at: http://localhost:5000
```

Before starting the backend, generate a unique JWT secret with
`node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`
and set `JWT_SECRET` in `backend/.env`. Startup rejects missing secrets, secrets
shorter than 32 characters, and the former shared development secret. Replacing
an existing secret invalidates existing sessions; users must sign in again.

Run isolated backend checks with `npm run test:unit` from `backend`, and frontend
catalog tests with `npm test` from `frontend`. Backend `npm run test:all` also runs
the integration scripts, which require a running test API and configured test
administrator credentials.

### Seed an Isolated Stakeholder Demo

The demo seed creates synthetic patient, medical staff, and admin accounts plus
sample records. Insurer companies and agents must use the real enrollment and company-admin
workflows; the seed does not create insurer access or claims. It also adds a seven-day, patient-approved clinical access grant so the
clinician workspace has a patient to review. The demo clinician uses an active hospital
already created by an administrator; set `DEMO_HOSPITAL_ID` to that hospital's ID.
Run the seed only against a dedicated development database, never a production or existing
user database. Set `NODE_ENV=development`, `MONGODB_URI` to that isolated database, and
`DEMO_SEED_PASSWORD` to a password of at least 12 characters before running:

```bash
cd backend
node seed_demo.js
```

The accounts use `patient@medivault.io`, `doctor@medivault.io`, and
`admin@medivault.io`; each uses the configured demo password. The generated clinical PDF
is explicitly marked as synthetic and is not for clinical or insurance decisions.

### 2. Setup Frontend

```bash
cd ../frontend

# Install frontend dependencies
npm install

# Start Vite development server
npm run dev
# Frontend will run at: http://localhost:5173
```

### Provision the First Administrator

Public sign-up is limited to patients and staff; administrator access cannot be self-requested.
After registering a trusted operator account as a patient, promote it from the backend using
an account with database access:

```bash
cd backend
npm run admin:promote -- operator@example.com
```

The operator can review organization enrollment applications and credentials for users that remain
platform-administered. Hospital-assigned physicians and nurses are handled by their hospital
administrator. Insurer agents are reviewed by their insurer's company admins; pharmacy and lab
staff are managed by the corresponding organization admins.

## ☁️ Deployment (Vercel Services + MongoDB Atlas)

The root `vercel.json` deploys the Vite frontend and Express API as separate Vercel
services in one project. Requests to `/api/*` are routed to the backend; all other paths
go to the frontend. The API remains a normal local Express server outside Vercel.

### Local development

- Run MongoDB locally and set `backend/.env` to use
  `MONGODB_URI=mongodb://127.0.0.1:27017/medivault`.
- Keep `frontend/.env` set to `VITE_API_BASE_URL=/api`; Vite proxies API and upload
  requests to the local backend.
- Start the backend and frontend using the setup steps above. New uploads are stored in MongoDB GridFS. `backend/uploads` is used only for legacy/demo files.
- Optional local AI summaries, medicine search, and insurer plan drafting use Ollama. Install Ollama, run
  `ollama pull qwen2.5:3b`, and start Ollama on `http://127.0.0.1:11434`. Set
  `OLLAMA_BASE_URL` and `OLLAMA_MODEL` in `backend/.env` if needed. The backend only
  accepts loopback Ollama URLs; AI requests stay on that local instance when `AI_PROVIDER=ollama`. English
  summaries for patients and authorized doctors and insurer plan suggestions are
  generated on demand and not stored. English OCR runs locally for images and
  scanned PDFs (up to three pages); searchable PDFs use their embedded text.
  Extracted text and an identity-consistency status are stored with each record
  to support clinician overviews. The check compares readable patient details
  with the account/profile and is only a review aid: a match does not prove a
  report is authentic, and uncertain or mismatching uploads remain available for
  manual review. OCR text is sensitive health data and is stored in the database.
  Hindi is not enabled because the current model output needs accuracy
  validation. AI summaries and OCR can be inaccurate and are not medical advice;
  verify findings against the original report with a healthcare professional.
- Run the local AI service tests with `cd backend && npm run test:ai`.

### Hosted deployment

1. Import the repository root into Vercel from GitHub. Keep the project root at the
   repository root so Vercel can read the top-level `vercel.json` and build both services.
2. Create a MongoDB Atlas cluster and database user. Configure Atlas network access so the
   Vercel backend can reach it. MongoDB is an external service; its URI is not a Vercel
   service binding.
3. Set environment variables for the backend service in Vercel:
   - `MONGODB_URI`: the Atlas connection string
   - `JWT_SECRET`: a unique, randomly generated production secret
   - `JWT_EXPIRES_IN`: for example, `7d`
   - `CLIENT_URL`: comma-separated exact origins only if the frontend is hosted separately
     from the API (for example, `https://app.example.com`). Same-origin Vercel service
     requests are allowed automatically; this variable is not needed for the bundled app.
   - `NODE_ENV=production`
4. The frontend uses the same-origin `/api` path, so it needs no backend URL binding and
   no `VITE_API_BASE_URL` override for this routing setup.
5. Deploy and check `https://your-app.vercel.app/api/health`.

New uploads are stored privately in the `medicalFiles.files` and `medicalFiles.chunks`
GridFS collections in the configured MongoDB database. No additional storage account or
new environment variable is required. The database user needs read/write and index-creation
permissions. Downloads still pass through authenticated API authorization, including
company and patient checks on insurance claim downloads. New uploads no longer depend
on Vercel temporary disk. Existing disk-backed records remain readable only while their
original files exist; missing files must be uploaded again.

Uploads are limited to 4 MB each (frontend and backend) to leave multipart overhead below
Vercel's 4.5 MB function payload limit. File signatures must match PDF, PNG, or JPEG;
this is not a malware scan. Files consume your Atlas storage allowance. Monitor cluster
usage during testing; object storage is the next step if document volume grows.

Login attempts are limited per 15-minute fixed window to 30 per IP and 10 per normalized
email address. Registration is limited to 10 attempts per IP per hour. Successful attempts
also count. Counters are shared in MongoDB, with TTL cleanup; a 429 includes Retry-After.
If counter storage fails, authentication returns 503 rather than bypassing the limit.
On Vercel, the platform-overwritten forwarding header identifies the client; other hosts
use the socket address. Configure trusted proxy handling before deploying behind another
proxy. Limits reset at window boundaries, so bursts can occur across a boundary.

Run `npm run test:unit` in `backend` for isolated checks. To run the storage integration
test against a dedicated local MongoDB server, set `TEST_STORAGE_MONGO_URI` to its
loopback URL (for example, `mongodb://127.0.0.1:27028`) and run `npm run test:storage`.
The test creates and removes its own randomly named database and never uses `MONGODB_URI`.

After deploying, upload a synthetic file, redeploy, and verify download and deletion with
the same account. Verify that another patient cannot download it. For deployed AI, configure Gemini as described below. Ollama mode requires a model service on the backend host.

Never commit `.env` files or expose production secrets in `VITE_*` variables. MediVault
handles sensitive health information; this deployment setup does not by itself make the
application compliant with healthcare privacy regulations. Do not use it for real
patient data until hosting, access controls, encryption, backups, and compliance have
been independently reviewed.

## 📡 API Reference Overview

### Separate Sign-In Portals
- The public home (`/`) is patient-facing and shows only patient sign-in (`/patient/login`) and patient registration (`/patient/register`).
- Medical staff, insurance agents, insurer admins, pharmacy managers, laboratory managers, hospital admins, and platform admins use separate sign-in paths. Insurer admins sign in at `/insurance/admin/login`; organization admins use their pharmacy or lab portal.
- Medical staff and insurance agents apply at `/clinical/register` and `/insurance/register`. Insurers enroll at `/insurance/company/register`; pharmacy and laboratory chains apply through their organization registration forms. Enrollment stays inactive until platform admin approval. The initial applicant keeps their chosen password; additional admins provisioned by a platform admin receive a temporary password that must be changed at first sign-in.

The sign-in forms accept only the account roles assigned to their portal. Backend role authorization remains the enforcement boundary for protected data and operations.

### 7. Pharmacy Organizations and Patient-Controlled Sharing

Hospitals and independent pharmacies apply to join the MediVault directory through a pharmacy manager account. Pharmacy and laboratory chain parents can self-enroll; a platform administrator reviews their registration and enables the initial applicant as a chain admin. The platform administrator can provision additional chain admins with temporary passwords that must be changed at first sign-in. Approved chain admins add and approve their own branches or locations and manage staff membership. Only currently valid, approved dispensing locations appear in the relevant directory. “MediVault-verified” means registration documents were reviewed and are currently valid. It is not a guarantee of dispensing quality, clinical outcomes, or service availability. Organization managers review pharmacist membership requests. Pharmacists must also pass MediVault credential review and account approval before accessing pharmacy workflows.

Insurers can self-enroll at `/insurance/company/register`. A platform administrator approves or rejects the company application and can provision additional insurer admins with temporary passwords. The initial company applicant keeps the password chosen during enrollment. Insurer admins review agent credentials and approve agent accounts for their own company. The platform administrator sees the company enrollment queue, while ongoing agent approval remains company-scoped.

Patients can direct a 24-hour share to a selected directory organization or create a one-time displayable access code for a pharmacist. The directory share is scoped to one organization; the first pharmacist at that organization to open it is bound to the share. Codes are intended for direct handoff and are bound to the first pharmacist account that redeems them.

## 🔒 Security & Privacy Features

- **Multi-Stakeholder RBAC**: Role enforcement for patients, clinical staff, insurer admins and agents, pharmacy/lab organization admins, hospital admins, and platform admins, plus physician/nurse capability checks for clinical actions.
- **Appointment-scoped nursing access**: Nurses can only read the authorized profile basics and append care entries for their assigned, confirmed appointment during its 30-minute-before to 30-minute-after window. Access is granted only by patient consent. Patient revocation and appointment cancellation close the backend access gate. The assigned physician can review nursing entries during the same appointment access window.
- **Dual-Context Caregiver Delegation**: Authorized proxies can switch context using the patient's MediVault ID in the `x-patient-context` header with granular `read_only` or `full` privileges.
- **Privacy-Preserving Insurance Verification**: Insurance agents can only inspect records explicitly attached to an active claim.
- **Insurance organization boundaries**: Agents can list, view, review, supplement, and download only claims for their insurer at hospitals assigned to their account. Insurer admins can manage claims and plans only for their company. Claims without an active hospital assignment stay in the insurer-admin queue. Plans are owned by an insurer record; provider names are set by the server.
- **Upload Validation**: Checks MIME types and file signatures for PDF, JPEG, and PNG; stores new documents in private GridFS storage under random identifiers.
- **Immutable Cross-Stakeholder Audit Trail**: Captures logins, proxy delegations, caregiver actions, claim submissions, claim reviews, and administrative changes with IP and user agent.

## Recent interface updates

- **Dashboard attention:** Links to pending, unexpired clinical access requests, claims needing more information, and up to five upcoming confirmed or pending appointments. Items follow the selected patient context; read-only caregivers do not receive access-approval prompts. Appointment times use India Standard Time.
- **Multi-file uploads:** Select or drop multiple PDF, PNG, or JPG documents (up to 4 MB each), review each title, category, date, and notes, and track per-file transfer and processing status. Titles are suggested from filenames; dates default to today. Retry failed entries without re-uploading successful entries.
- **Duplicate warnings:** Match filename, size, and modification time within the current upload queue only. Existing vault records are not checked for duplicates.
- **Medication display:** Ongoing medications come from the health profile. Recent prescriptions are displayed separately without inferring whether treatment is active or completed.
- **Appointment nursing access:** Patients can assign a same-hospital nurse at booking or for an upcoming appointment and approve limited access. Assisted bookings by nurses do not grant access; the patient must approve it. Nurses see their assigned visits, authorized profile basics, and appointment-linked nursing notes/observations; the assigned physician sees those entries during the same appointment access window.
- **Nurse operations without patient-record access:** Nurses can maintain their shift availability and self-reported training, view a same-hospital roster with aggregate workload counts, and share reusable checklists or operational handovers that are not attached to patients. Patient names and IDs are hidden from the nurse appointment list until the consented access window opens.
- **Professional profile preview:** Patients can view the public professional details of each physician or nurse offered by the appointment directory before selecting a care team member.
- **Stakeholder account profiles:** A My Profile navigation option is available to patient, clinical staff, insurance agent, and administrator accounts. Patient health profile editing remains patient-specific; other roles see their own account, credential, or insurer details.
- **Consistent audit activity:** Patient and stakeholder activity logs share the same event list, event-type and date filters, actor details, and pagination. Stakeholder IP and resource columns were removed from the main view to reduce visual clutter; audit records remain available to the backend and administrators.
- **Indian emergency contacts:** A fixed `+91` prefix accompanies exactly 10 national digits. Frontend and backend validation enforce this format; numbers are saved as `+91XXXXXXXXXX`. The phone field remains optional.
- **Consistent typography:** Self-hosted Source Sans 3 is used throughout app text, headings, IDs, forms, and numbers.
- **Light theme:** White cards, a cool grey background, burgundy actions, soft rose highlights, stronger borders, and tighter dashboard spacing. Dark mode retains its existing palette. Styles live in `frontend/src/index.css`.

## Notifications, claim progress, and appointment cancellation

- The patient portal includes an inbox of the latest 50 recorded appointment (including staff-assisted booking), claim, access, and clinical-note events. It refreshes every 30 seconds and stores read receipts separately for each viewer. Read-only caregivers can view updates but cannot mark them read. Notifications are in-app only and depend on successful audit-event recording.
- Claim progress shows dated status and remark entries for new submissions, reviews, and supplemental authorizations. Older claims identify missing historical steps. Approval is not presented as confirmation of payment.
- Patients and full-access caregivers can cancel future pending or confirmed appointments after confirmation. Cancellation atomically releases the slot, retains the appointment as cancelled, and records the actor and timestamp. Past, declined, and already-cancelled appointments cannot be cancelled again.
- Run `node --test backend/test_appointment_cancellation.js backend/test_dashboard_attention.js` for focused cancellation, claim-history, and dashboard checks. These use mocked database operations and schema validation, not a live database.

## Indian locale conventions

- Display dates use `en-IN` (day first); timestamps and appointment schedules use `Asia/Kolkata` (IST), independent of device timezone.
- Appointment booking interprets hospital slots in IST. Access-expiry form values are converted from IST to UTC for API storage.
- Currency uses INR and Indian digit grouping (for example, `1,23,456`). Claim notifications and validation messages also use INR.
- Emergency contact numbers use fixed `+91` followed by 10 digits.
- Native date/time pickers may render their controls according to browser settings; API date values remain ISO-formatted. Existing audit message text is preserved.


## Gemini on Vercel (demo)

Save `GEMINI_API_KEY` as a backend secret in Vercel and redeploy. With no explicit
`AI_PROVIDER`, a nonempty Gemini key selects Gemini; otherwise the app uses local
Ollama. `AI_PROVIDER=gemini` or `AI_PROVIDER=ollama` overrides this selection.
`GEMINI_MODEL` defaults to `gemini-3.5-flash-lite`. Confirm that this model has free
quota in your Google AI Studio project. The app does not enable billing, change your
Google account tier, or fall back to another provider/model. Actual availability,
pricing and quota are controlled by Google, not these environment variables.

All four API operations (patient document summary, clinician overview, medicine
catalog matching, and insurance draft assistant) use the same provider adapter.
PDF/OCR extraction remains on the backend. Gemini receives extracted record or
clinical-context text for summaries, search phrases and catalog candidates for
matching, and conversation text for insurance drafting. The interface shows the
active provider's disclosure before enabling AI actions. Use synthetic data only
with Gemini's free tier; content may be used to improve Google products. Summaries
are not saved by MediVault; this does not describe the provider's retention policy.
Never put API keys in frontend variables, source code, logs, or chat messages.

MongoDB-backed limits apply across instances: 5 attempts/user/minute, 20/user/day,
10 overall/minute, and 100 overall/day. Configure these using the `AI_*` variables
in `backend/.env.example` to match your project's actual quota. Daily windows reset
at UTC midnight (05:30 IST), independently of Google's quota reset. Failed requests
also consume budget. One active AI operation per user is allowed, with a 90-second
lease; requests time out after at most 45 seconds (20 seconds for catalog search).
Limits and leases fail closed if MongoDB is unavailable. No automatic retries are
made. Provider quota exhaustion returns 429; normal record access remains available.

`GET /api/ai/config` requires sign-in and returns only provider, model and whether
processing is external. It never returns a key. AI errors do not log provider bodies,
prompts, responses, or credentials. Test with `npm run test:unit` in `backend`;
Gemini requests are mocked, so these tests never use a real cloud API key.

After deployment, sign in, confirm the Gemini disclosure, and summarize a synthetic
report. Check the insurer assistant and medicine search too. A 503 configuration
message means the administrator should check the key, exact model ID and project
access; a 429 means a provider quota or application usage limit was reached.
